# Memory-level .gitignore template (v4.12.0+)

When `memory-as-git` is enabled, `<config-root>/memory/` becomes a git repository. A memory-specific `.gitignore` lives at `<config-root>/memory/.gitignore` and governs what's tracked WITHIN the memory repo. (The parent-level `.gitignore` at `<config-root>/.gitignore` — from v4.7.2 — still governs the parent directory's exclusions like `archive/`, `briefs/`, `plugins/`.)

Written by `/setup-identity` Step 3.6 (init) and re-applied by `/end-day` Step 5.8 if missing.

**Important syntax note (v4.12.1 bugfix):** `.gitignore` does NOT support inline comments on the same line as a pattern. `pattern # comment` is parsed as a literal filename `pattern # comment`, not a pattern with an explanation. Every comment line must START with `#` and live on its own line.

## Two variants (v4.12.2+)

The template ships in two variants. `/setup-identity` Step 3.6 step 6 picks one based on whether the user configures a remote:

- **local-only** (default — no remote configured) — tracks everything not actively churning. Includes `triage-log.md` and node-level changelogs for local audit grep.
- **remote-safe** (chosen when `memory_as_git.remote:` is set) — additionally excludes PII-dense files that should never leave the machine: `triage-log.md`, `dismissed-proposals.log`, and any symlinked `*.user-context.md` inside memory/.

If a user adds a remote AFTER initial init (via re-running `/setup-identity` or hand-editing `cortex.user-context.md`), the next `/end-day` Step 5.8 detects the change, regenerates `.gitignore` from the remote-safe variant, and runs `git rm --cached` on the newly-excluded files before the commit.

## Template — local-only variant (default)

Emit this EXACT content; do not re-format. The blank line below the opening fence is intentional.

```gitignore
# memory/.gitignore — local-only variant
# Generated by cortex /setup-identity Step 3.6 (memory-as-git init)
# v4.12.2: comment lines start with # on their own line; do NOT inline.

# Operational state (changes every tick; would dirty every diff)
.state.json

# Write-lock marker (v4.12.2+) — flags an in-progress memory mutation
.write-lock

# Operations chronicle — too noisy for daily diff review
log.md

# Staged drafts (reviewed elsewhere; only the merged outputs land in committed memory)
staged/

# 7-day rolling cache; refreshed by /listen, /morning, /end-day
hot.md

# Auto-maintained catalog; refreshed by indexer skill
index.md

# Person-mention counter (rebuilt by /relink-memory and /end-day)
.person-mention-counts.json
.person-recall-counter.json

# Deprecated pre-v4.8.1 staged-substrate dotfiles (kept here for back-compat; remove after one stable release)
.commit-drafts/
.research-drafts/
.rehearse-queue.md
.rehearse-skip-log.md
.research-skip-log.md
.morning-reject-log.md
.reindex-queue
```

## Detecting remote-promotion (v4.12.2+)

`/end-day` Step 5.8 reads `cortex.user-context.md` `memory_as_git.remote`. If set AND `memory/.gitignore` matches the local-only fingerprint (contains `log.md` line but does NOT contain `triage-log.md` line), it:

1. Rewrites `.gitignore` to the remote-safe variant.
2. Runs `git rm --cached triage-log.md dismissed-proposals.log 2>/dev/null` (silently ignore errors for files not tracked).
3. Stages the changes for inclusion in today's commit.
4. Surfaces to the user: "Memory-as-git remote configured → promoted to remote-safe gitignore. Un-tracked: triage-log.md, dismissed-proposals.log. These files stay on your machine but no longer ride to the remote. (Already-pushed commits containing them remain on the remote — see Remote-rewrite section below.)"

## What stays IN the committed memory repo

After this gitignore applies, the committed surface is:

- `user.md` — user profile
- `DASHBOARD.md` — active-state overview
- `.decay-config.md` — decay thresholds (user-edited, semantically meaningful)
- All node directories with their content:
  - `client/*.md`, `person/*.md`, `topic/*.md`, `workstream/*.md`, `bizdev/*.md`, `team/*.md`
  - Unprefixed root-level nodes
- `archive/` — historical nodes (the cortex archive, not the raw-substrate archive at `<config-root>/archive/`)
- `triage-log.md` — commit-triage decisions (semantically meaningful even though log-shaped)

## Migration from pre-v4.12.0 installs

If a pre-existing install already had `hot.md` or `index.md` tracked in git (unlikely — most installs haven't initialized git), the migration step is:

```
cd <config-root>/memory
git rm --cached hot.md index.md staged/ 2>/dev/null
```

(ignore errors if not tracked)

This removes them from the index without deleting the files. Subsequent commits won't include them.

## Migration from v4.12.0 installs (broken inline-comment template)

If `/setup-identity` Step 3.6 ran under cortex v4.12.0 (released 2026-05-28), the resulting `memory/.gitignore` had inline comments which `.gitignore` parses as literal filenames — meaning the intended exclusions (hot.md, index.md, log.md) were silently NOT excluded. Affected files committed unintentionally.

`/setup-identity` Step 3.6 in v4.12.1+ detects the bad template by reading `memory/.gitignore` and checking whether any line contains `#` after a non-`#` character (inline-comment pattern). If found:

1. Rewrite `memory/.gitignore` from the corrected template above.
2. Run `git rm --cached hot.md index.md log.md .state.json .person-mention-counts.json .person-recall-counter.json 2>/dev/null` to remove them from the index.
3. Commit the cleanup as `cortex v4.12.1 — fix memory/.gitignore inline-comment parsing; un-track cache files`.

`/end-day` Step 5.8 in v4.12.1+ also detects this on every run as a defensive measure (handles users who ran `/setup-identity` on v4.12.0 and never re-run it).

## Why exclude `hot.md` and `index.md`

Both are deterministic re-renders of the rest of memory:
- `hot.md` = top 3K words of recent content from active nodes, regenerated by `/listen`, `/morning`, `/end-day`.
- `index.md` = catalog of all nodes with decay flags, regenerated by indexer skill.

If the underlying nodes are in the diff, hot+index are derivable. Including them in commits would drown out the signal — every day every commit would show large hot.md churn that's just "regenerated, same data."

## Why exclude `log.md`

`log.md` is the operations chronicle (`## [YYYY-MM-DD HH:MM] <op> | <subject>` entries appended by 9+ commands). Changes every command run. Including it would make every commit show log churn — not knowledge changes.

The log still exists as a grep-able chronicle. It just doesn't ride along with the memory git history.

## Why exclude `staged/`

Per `references/migrations.md` (v4.8.1+), staged is the in-flight memory state pre-review. Once a proposal is merged via `/morning` or `/cleanup`, the merge writes to memory node files which DO get committed. Tracking `staged/` would double-count work and create noisy diffs (every `/listen` would produce a diff that then gets superseded the next morning).

## Remote-rewrite section (v4.12.2+)

If a user was on cortex v4.12.0 and ran `/end-day` → `git push origin main` BEFORE the v4.12.1 fix landed, their remote repo carries one or more commits containing `hot.md`, `index.md`, `log.md`, etc. Self-heal on the LOCAL repo (the v4.12.1 fix) does NOT rewrite remote history.

`/setup-identity` Step 3.6 step 4b (and `/end-day` Step 5.8) detect this case via:

1. `git config remote.origin.url` returns a value (remote is configured).
2. `git log --oneline origin/main` is non-empty (user has pushed at some point).
3. Either the local repo has the v4.12.0 fingerprint OR the remote-safe gitignore is now being applied locally for the first time.

If all three: surface a one-time remediation prompt:

> "Pre-v4.12.2 commits with high-churn or PII-dense files (hot.md, index.md, log.md, possibly triage-log.md, dismissed-proposals.log) exist on your remote at `<remote-url>`. Local repair has un-tracked them going forward, but already-pushed history retains them. To purge:
>
>   git filter-repo --invert-paths --path hot.md --path index.md --path log.md --path .state.json --path triage-log.md --path dismissed-proposals.log
>   git push origin main --force
>
> This rewrites history. Only do it if you're the sole user of the remote. If others have cloned it, coordinate first. See https://github.com/newren/git-filter-repo for filter-repo install."

Mark a `<config-root>/memory/staged/skip-logs/remote-remediation-acknowledged` marker after surfacing once. Subsequent runs check this marker and skip.

This is NOT auto-executed because force-push is destructive and the user may have collaborators on the remote. Surfacing is the right behavior; user takes action manually.
